# Manifest, state and signing

**Purpose:** How the served manifest is built, how devices pick a patch (bucketing, ladder, selection), how state versions and the audit chain make history tamper-evident, and how signing and anti-replay work.
**Audience:** Engineers touching `ota-core`, native ports, or the deploy job; reviewers of security properties.
**Source of truth:** [`packages/ota-core/src/`](../../packages/ota-core/src/) (`manifest.ts`, `bucket.ts`, `ranges.ts`, `ladder.ts`, `select.ts`, `state.ts`, `audit.ts`), [`job.ts`](../../packages/ota-cli/src/job.ts), conformance vectors [`packages/ota-core/vectors/`](../../packages/ota-core/vectors/), device side [`native/otacore/runtime/src/runtime.cpp`](../../native/otacore/runtime/src/runtime.cpp). Rationale: [DESIGN.md](../../DESIGN.md) sections 5.2, 5.5, 6, 7.1, 8, 10. Field-level formats: [file-formats.md](../reference/file-formats.md).

## 1. One static manifest per (platform, app version)

The CDN serves `<cdn>/<platform>/<appVersion>/manifest.json` plus `manifest.json.sig` (see [file-formats.md#manifest](../reference/file-formats.md#manifest)). There is no server logic: the file is identical for all devices; each device decides locally which patch applies to it. The served manifest IS the deployable state (no state file in git). Per-unit consistency, not per-session consistency, is the contract: units have no edges between them, so a unit may be pinned from an older snapshot than another (DESIGN.md 5.5).

## 2. Bucketing (device side, stable)

`bucket(deviceId, unitName)` in [`bucket.ts`](../../packages/ota-core/src/bucket.ts):

```
h      = SHA-256( UTF-8(deviceId) || 0x0A || UTF-8(unitName) )
bucket = uint32_big_endian(h[0..4]) / 2^32        // in [0,1), exact double
```
The host uses `hostBucketKey` (default `"mainBundle"`) as the "unit name" (DESIGN.md 5.8 decision 12). `deviceId` is a random install-scoped UUID that never leaves the device, so the CDN sees only anonymous conditional GETs. Native ports must match bit for bit: [`vectors/bucket.json`](../../packages/ota-core/vectors/bucket.json) (24 vectors, generated by [`scripts/gen-vectors.ts`](../../packages/ota-core/scripts/gen-vectors.ts)); tests: `core.test.ts` "bucket matches conformance vectors", native `test_hashing`/`test_manifest`.

## 3. Ranges and the rollout ladder

An entry's `range` is half-open `[start,end)` over the bucket; absent means `[0,1)`. Invariant (validated): non-empty ranges of one unit are disjoint (sum <= 1). Unassigned buckets get the embedded bundle. Percent -> fraction goes through basis points (`percentToFraction`: 0..100, two decimals).

Entries are ordered newest first and laid out from bucket 0: `[0,x) newest | [x,y) previous | [y,1) embedded` ([`ladder.ts`](../../packages/ota-core/src/ladder.ts)). All functions are pure.

| Operation | Function | Effect |
|---|---|---|
| deploy | `addPatch` | new entry at the FRONT with range `[0,0]` (0%); older entries keep their ranges; duplicate id throws |
| ramp | `setPercent(id, p)` | only the newest may be ramped (else throws "ramp is only allowed for the latest patch"); sets `[0,p]`, older entries re-laid out to start where the previous ends; entries left with an empty range are retired (never the newest); users only move forward |
| halt | `halt(id)` / `setPercent(id, 0)` | the entry is REMOVED (there is no `halted` flag); if it was the newest, the next one is extended back to bucket 0 so users return to what they had; halt works on any entry |
| restore | `applyRestore` | content of an earlier state version published as the next version |

Tests: `core.test.ts` "ladder: ..." (4 tests) and "state: deploy -> rollout -> halt -> restore keeps invariants and monotonic versions".

## 4. Device selection

`selectUnit` / `selectHost` in [`select.ts`](../../packages/ota-core/src/select.ts) (mirrored in C++, `native/otacore/src/select.cpp`; parity vectors [`vectors/select.json`](../../packages/ota-core/vectors/select.json), 32 cases per DESIGN.md 5.7). Order of decisions:

1. `patchAlgoVer` not in `supportedAlgos` -> embedded (`algo-unsupported`)
2. unit absent from manifest -> embedded (`unit-not-in-manifest`)
3. manifest `baseHash` != the embedded hash -> embedded (`base-mismatch`)
4. the entry whose range contains the bucket owns the device; none -> embedded (`no-range-match`)
5. owner has `requiresHost` different from the host id the running VM booted with -> embedded (`requires-host-mismatch`); v1 does NOT fall back to an older patch
6. otherwise the patch (`ok`)

For the host, `runningHostId` is forced to `embedded` (`requiresHost` is meaningless there). The per-VM pin that follows selection is client-runtime behavior: [05-client-runtime.md](05-client-runtime.md).

## 5. State versions

`ota-state/<appVersion>/v<N>/` holds both platforms' manifests, their signatures and `audit.json` (layout: [file-formats.md#state-layout](../reference/file-formats.md#state-layout)). Rules implemented in [`state.ts`](../../packages/ota-core/src/state.ts):

- `initState` -> v1 for both platforms (empty entries, `ttlSec` default 120, host `baseHash` from `base.json`).
- Every command produces exactly version `prev+1`; both platforms get the same number even when only one platform's entries changed (`withVersion` re-stamps `version`). The result is validated (`validateManifest`) before signing.
- `deploy` takes a patch per AFFECTED platform; the other platform gets no entry. `rollout`/`halt` default to the platforms where the patch id exists (`scope`), error if a requested platform lacks it, error `unknown patch`.
- Units are added to the manifest lazily on first deploy using `base.json` (unit must exist in the base release, else `unknown unit`).
- `restore` copies an earlier version's manifests as `N+1` (version stays monotonic). Restoring requires the old version's signature to verify.
- The store forbids overwriting a version (create-if-absent) and the job holds a per-app-version lock: see [ports-and-adapters.md](../reference/ports-and-adapters.md).

Rollback = redeploy an earlier state (`rollout 0`/halt, or `restore`). Procedures: [incident-runbook.md](../guides/incident-runbook.md).

## 6. Audit hash chain

Every state version has one `AuditRecord` ([`audit.ts`](../../packages/ota-core/src/audit.ts)): `command`, `unit`, `patchId`, `params`, `requester`, `approver`, `breakGlass`, `ticket`, `pr`, `sourceSha`, `jobUrl`, `ts`, plus `previousVersion` and `prevAuditHash = sha256(canonicalize(previous record))`. `verifyAuditChain` re-computes the chain and reports `previousVersion` gaps and hash mismatches. `ota-cli verify` also checks `audit.stateVersion == N`, manifest `version == N`, platform/appVersion, signatures, contiguity of versions and CDN consistency (`verifyStore`). Tests: `core.test.ts` "audit chain ...", `job.test.ts` "tampered audit history is detected".

Caveat (code): the chain is tamper-EVIDENT within the store; it is not itself signed. The signed manifests plus store immutability and write-access limited to the deploy job are what protect it. DESIGN.md 7.7 also mentions a Jenkins-held KMS signature over the state ("Provenance"); the code signs manifests only, not `audit.json`. Treat that as planned.

## 7. Signing

- Algorithm: Ed25519, detached, base64 (`signManifest`, `verifyManifestBytes`). The signed bytes are the canonical JSON string (`canonicalize`: keys sorted recursively, no whitespace, `undefined` dropped, non-finite numbers throw). Those exact bytes are stored in `ota-state`, served as `manifest.json`, and verified; **devices verify the received bytes first, then parse**, so they never canonicalize.
- `platform` and `appVersion` are inside the signed bytes (no cross-platform/version replay).
- The job refuses to sign an invalid manifest and, on every command, re-verifies the signature of the latest stored state over the stored bytes before building on it ("refusing to build on tampered state"). Tests: `core.test.ts` "detached signature over served bytes"; `job.test.ts` "tampered state is refused and detected by verify".
- Production key is meant to live in KMS behind `SignerPort`; the local signer holds a PEM. Multiple embedded public keys / key ids are planned (DESIGN.md 5.8).
- Pair window: manifest and `.sig` are two objects; see CdnPort invariant 2b in [ports-and-adapters.md](../reference/ports-and-adapters.md) and treat a mismatch as transient.

## 8. Anti-replay and freshness on the device

Implemented in the C++ orchestrator (`accept()` in `runtime.cpp`), in this order: verify signature -> parse/validate -> `platform` and `appVersion` equal the binary's -> `version < highestManifestVersion` rejected as replay -> same version ignored -> persist `highestManifestVersion` BEFORE adopting (fail closed if it cannot be stored) -> persist manifest/signature -> swap the in-memory snapshot atomically. A legitimate restore is published as N+1, so it passes. `ttlSec` bounds how long a device waits before re-fetching (conditional GET, jittered; halt latency = job time + `ttlSec`). Tests: `native/tests/runtime/scn_manifest.cpp` (`rejected_manifests_keep_old`, `cached_manifest_used_immediately_refresh_later`). Ed25519 verification itself is a platform-glue interface (`SignatureVerifier`); native CryptoKit/`java.security` implementations are not written yet ([native-api.md](../reference/native-api.md)).

## 9. Invariants checklist

| Invariant | Enforced by |
|---|---|
| `version` = state N, monotonic | `withVersion`, `validateManifest`, store create-if-absent, device `highestManifestVersion` |
| ranges disjoint, `start <= end` | `validateManifest` |
| only newest patch ramps | `setPercent` |
| `requiresHost` names a host entry | `validateManifest` |
| unit patches only for units in `base.json` | `applyDeploy` |
| retired versions accept only halt | `runCommand` (break-glass also allowed) |
| signed bytes == served bytes == stored bytes | `signManifest`, store invariant 4, CDN invariant 4, `verifyStore` |
