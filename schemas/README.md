# schemas/

Machine-readable contracts (JSON Schema draft 2020-12, hand-written) for every JSON file the OTA tooling reads or writes.
They are validated in CI against **real** artifacts: `packages/ota-core/test/schemas.test.ts` loads `schemas/fixtures/*.json`
(generated by running the actual pipeline, see below), checks the negative cases, and checks that the schemas do not drift
from the TypeScript types in `packages/ota-core/src/types.ts` and from the splitter's `DEFAULT_CHECKS`.

| Schema | Validates | Produced by | Consumed by |
|---|---|---|---|
| `manifest.schema.json` | signed served manifest `<cdn>/<platform>/<appVersion>/manifest.json` (DESIGN.md 6; type `Manifest`) | `ota-cli` (state transitions in `ota-core`) | native SDK, `ota-cli verify`, `ota-core select` |
| `units.config.schema.json` | **splitter input** `units.config.json` at the app root: unit roots/entries + `checks` | humans (app repo) | `unit-splitter`, `ota-build bundle` |
| `units.output.schema.json` | **splitter output** `<out>/units.json`: module ids per host/unit, cycles, warnings, check summaries, public API | `unit-splitter` | `ota-build` (copied into the build dir), next patch build as "base" |
| `build.schema.json` | `<build dir>/build.json` (hbc files + hashes + toolchain) | `ota-build bundle` | `ota-build patch / base-info` |
| `patch-report.schema.json` | `<patch dir>/patch-report.json` | `ota-build patch` | `ota-build deploy-args` -> `ota-cli deploy` |
| `base.schema.json` | `ota-base/<appVersion>/base.json` (`BaseInfo`) | `ota-build base-info` | `ota-cli init`, size limits at deploy |
| `audit.schema.json` | `ota-state/<appVersion>/v<N>/audit.json` (`AuditRecord`) | `ota-cli` | `ota-cli verify` (hash chain), humans |
| `ota-units-governance.schema.json` | **governance** `units.json` of the ota-deployments repo (`UnitsConfig`) | humans (PR reviewed) | `ota-cli --units`, authorization (`authz`) |
| `pin.schema.json` | `ota-deployments/<appVersion>/<unit>.json` = `{branch, sha}` (`Pin`) | humans / release job | CI verify (`validatePin`) |

## Three different files are called `units.json` / `units.config.json`

| Name | Where | Direction | Schema |
|---|---|---|---|
| `units.config.json` | app project root | splitter **input** (what is a unit) | `units.config.schema.json` |
| `units.json` | splitter `--out` dir / build dir | splitter **output** (which modules ended up where) | `units.output.schema.json` |
| `units.json` | root of the ota-deployments repo | **governance** (owner teams, Jira keys, size limits) | `ota-units-governance.schema.json` |

Each schema's `description` repeats this warning. Do not point an editor at the wrong one.

## What a schema cannot express (enforced in code instead)

Every schema's `description` lists its gaps. In short: cross-field and cross-document invariants.

- manifest: ranges of one ladder must not overlap, `start <= end`, ids unique, `requiresHost` must name a mainBundle entry (`validateManifest`)
- audit: the hash chain and `previousVersion` continuity (`verifyAuditChain`)
- pin: `branch` must match the unit/version in the file path (`validatePin`)
- governance: a Jira key maps to one unit only (`validateUnitsConfig`)
- units.config: disjoint roots, entry under a root and existing, `publicApiSnapshot` keys listed in `publicPackages` (splitter `config.js` / `checks.js`)
- units.output: id sets disjoint, `paths` target existing units
- patch-report: `hostChanged` / `changedUnits` consistent with `items`
- base: `units` and `sizes.units` have the same keys
- build: referenced files exist and match their hash (`verifyBuildDir`)

## IDE autocomplete (Cursor / VS Code)

Option 1, per file: add a `$schema` to files you edit by hand (allowed by `units.config`, `ota-units-governance` and `pin`):

```jsonc
// <app>/units.config.json   (path relative to the file)
{ "$schema": "../../schemas/units.config.schema.json", "units": [] }
```

Do not add `$schema` to machine-written, closed formats (manifest, audit, build, ...): the manifest is signed byte for byte.

Option 2, no file edits: workspace `.vscode/settings.json` (Cursor reads the same file):

```jsonc
{
  "json.schemas": [
    { "fileMatch": ["**/units.config.json"], "url": "./schemas/units.config.schema.json" },
    { "fileMatch": ["**/dist/units.json", "**/build*/units.json"], "url": "./schemas/units.output.schema.json" },
    { "fileMatch": ["**/ota-deployments/units.json", "**/governance/units.json"], "url": "./schemas/ota-units-governance.schema.json" },
    { "fileMatch": ["**/build.json"], "url": "./schemas/build.schema.json" },
    { "fileMatch": ["**/patch-report.json"], "url": "./schemas/patch-report.schema.json" },
    { "fileMatch": ["**/ota-base/*/base.json", "**/base.json"], "url": "./schemas/base.schema.json" },
    { "fileMatch": ["**/ota-state/*/v*/audit.json"], "url": "./schemas/audit.schema.json" },
    { "fileMatch": ["**/ota-state/*/v*/*/manifest.json", "**/manifest.json"], "url": "./schemas/manifest.schema.json" },
    { "fileMatch": ["**/ota-deployments/*/*.json"], "url": "./schemas/pin.schema.json" }
  ]
}
```

Adjust the globs to your repo layout (the two `units.json` files cannot be told apart by name; use directories as above).
The `$id`s use the placeholder host `https://ota.example/schemas/`: when moving the schemas into the work project, replace it
with a real URL (or keep it: nothing fetches it, ajv resolves by `$id` from the registered files).

## Example

```jsonc
// schemas/fixtures/pin.json
{ "$schema": "../pin.schema.json", "branch": "ota/cabs/11.9.0", "sha": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb" }
```

Every file in `fixtures/` is a real artifact; `fixtures/units.config.json` spells out every `checks` key at its default.

## Fixtures and tests

```bash
npm run schemas:fixtures   # = node scripts/gen-schema-fixtures.mjs
                           #   runs examples/demo-app through ota-build bundle/patch/base-info and ota-cli init/deploy/rollout in
                           #   .work/schema-fixtures (deleted afterwards), then rewrites schemas/fixtures/*.json. Needs the external
                           #   tools (scripts/fetch-tools.sh, scripts/native-build.sh --tools). Deterministic (fixed shas, fixed clock).
npm run schemas:test       # or: cd packages/ota-core && npm test   (the schema tests run with the rest of ota-core)
```

The fixture manifest is pretty-printed for readability; the served bytes are canonical JSON (sorted keys, no whitespace).
When you change a producer's output or a TS type: update the schema, regenerate the fixtures, and let `schemas.test.ts` tell you
what drifted. The validator is `ajv@8.17.1` (dev dependency of `packages/ota-core` only), class `ajv/dist/2020`, strict mode.
